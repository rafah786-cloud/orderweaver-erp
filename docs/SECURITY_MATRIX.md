## Interpretation and verification rules

- **Defining migration** is the earliest CREATE TABLE declaration detected in the static source scan; dynamic SQL and unusual syntax can require manual correction.
- **RLS enabled** means the explicit declaration must be traced through later migrations. `unknown` is not a pass.
- **Policies / grants** must be reviewed in migration order, including DROP/ALTER, permissive-versus-restrictive policy composition, PUBLIC/anon/authenticated/service_role grants, SECURITY DEFINER functions and execute privileges.
- **Company / branch scope** must be proved from the effective predicate and linked-record constraints, not from the mere existence of `company_id` or `branch_id`.
- **Audit coverage** requires checking all write paths, trigger behavior, actor provenance, before/after snapshots, sensitive-field redaction and append-only permissions.
- **Approval enforcement** requires proving direct DML/RPC bypasses are denied and that the domain transaction rechecks invariants at execution time.
- Run `python docs/tools/migration_security_matrix.py --markdown docs/SECURITY_MATRIX.generated.md --csv docs/SECURITY_MATRIX.generated.csv` from the repository root to produce a reproducible static inventory. Generated outputs should be compared to this reviewed matrix; dynamic SQL must be reviewed manually.
