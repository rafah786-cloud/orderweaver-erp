# Velocity Shipping safe increment

## Verified official contracts (11 October 2026)
- Authentication: https://www.velocity.in/shipping-faq/api/authentication
- Serviceability: https://www.velocity.in/shipping-faq/api/serviceability
- Rates: https://www.velocity.in/shipping-faq/api/rates
- Warehouse creation only: https://www.velocity.in/shipping-faq/api/warehouse

The authentication page documents Bearer API keys and the deprecated username/password endpoint returning `token` and `expires_at`. Its current sample does not return `valid_until`. The serviceability sample uses an older header format; the centralized client follows the current authentication page's Bearer requirement.

Serviceability and forward/return rates are read-only provider queries, not shipment booking. Rates preserve documented charge names; no undocumented currency, tax or all-in total is inferred. Runtime schemas discard unknown response fields and fail closed on missing required documented fields.

## Configuration and authorization
Existing `VELOCITY_USERNAME` and `VELOCITY_PASSWORD` remain server-side for the legacy token flow; configured names were verified, not their values. The repository supports `VELOCITY_API_KEY` with the documented Bearer header. Runtime status note (24 October 2026): the owner reports saving `VELOCITY_API_KEY` in the existing Lovable project's Secrets, but the connected repository tools cannot inspect secret values or prove that the published runtime uses this revision and secret. Treat effective configuration and provider authentication as unverified until a controlled Admin request succeeds. API keys are not generated by this app. Never put credential values in source control or chat.

All server functions require verified authentication and both approved status and admin role, checked through the caller's authenticated client. Existing warehouse reads retain RLS. Token-cache operations alone use privileged access after authorization. No database migration, production business-data write, or deployment was performed for this increment.

## Safety and limitations
- Fixed HTTPS provider origin, no redirects, 15-second timeout per HTTP attempt including body consumption, 1 MiB response cap.
- Fixed structured errors; no raw response errors, credentials, tokens, provider headers, or request bodies in diagnostics/logs.
- One retry after 401 for legacy sessions only. Re-read the shared token cache before refreshing to reuse an already-replaced token. No retries for 403, 429 or other failures; API keys are not refreshed using account passwords.
- Legacy session refresh is not serialized across worker instances. Concurrent token issuance can revoke another in-flight token. The existing schema has no distributed refresh lease; a supported API key avoids this issue. Production concurrent legacy-session use remains a blocker until API-key configuration or a separately reviewed distributed-refresh migration.
- Warehouse list paths/field aliases in the old implementation were guesses. Sync now fails closed; existing saved rows are untouched. The official warehouse page documents POST creation, not a GET list response contract.
- No automatic API calls on page load beyond saved-warehouse reads. Admin checks use entered pincodes/dimensions. No live booking, shipment writes or arbitrary API proxy.
- No real provider success is claimed until an admin submits a check and the exact documented response validates. Unit fixtures are test-only, never app data.

## Deployment and checks
